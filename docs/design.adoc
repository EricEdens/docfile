= Design

[abstract]
A portable MS-CFB reader that behaves like Windows' compound file
implementation.

== Goals

We're building a file explorer for Windows, Linux, and macOS. Several of the
file formats we want to read are {url-ms-cfb}[MS-CFB] containers under the
hood:

* {url-ms-doc}[Word 97-2003 documents] (`.doc`).
* {url-ms-xls}[Excel 97-2003 workbooks] (`.xls`).
* {url-ms-ppt}[PowerPoint 97-2003 presentations] (`.ppt`).
* {url-ms-oxmsg}[Outlook items] (`.msg`).
* {url-msi}[Windows Installer packages] (`.msi`).
* {url-msp}[Windows Installer patches] (`.msp`).

If we only cared about Windows, this part would be easy. We'd use
{url-compound-files}[Microsoft's compound file implementation] through
{url-istorage}[IStorage], {url-istream}[IStream], _et al_. Microsoft even has
an {url-fib-example}[example for Word 97-2003 files] that shows how: open the
storage, open the `WordDocument` stream, and read it through `IStream`. We'd
get the _same_ implementation Word uses, with very little work on our side.

But we also want to open those files on Linux and macOS. That leaves us looking
for a portable reader, and there are already several to choose from. So why
write _another_ one?

Some of them bring a whole runtime along. {url-olefile}[olefile] requires
Python, and {url-poi}[Apache POI] requires a JVM. Neither fits our application.
{url-libgsf}[libgsf] pulls in GLib and GObject, and its licensing would make us
re-think using MIT. It also doesn't aim to match Windows' reading behavior.
Neither does the Rust {url-cfb-crate}[cfb] crate.
